# RC-002 Telemetry Model

## Document Information

**Project:** RC-002 — Enterprise Network Security Observability and Telemetry  
**Project Aegis Phase:** OBSERVE  
**Document Version:** 0.1  
**Status:** Initial Telemetry Model

---

## 1. Purpose

This document defines the categories of network and security-relevant
information that RC-002 intends to observe.

The telemetry model is technology-neutral.

Its purpose is to identify what information is required before selecting
the technologies used to collect, transport, store, and analyze that
information.

---

## 2. Telemetry Model

RC-002 organizes telemetry into five logical categories:

1. Network infrastructure telemetry
2. Network communication telemetry
3. Security-control telemetry
4. Host and service telemetry
5. Experimental-context telemetry

These categories collectively provide the observational foundation for
RC-002.

---

## 3. Network Infrastructure Telemetry

### Purpose

Observe operational state and significant changes occurring within
network infrastructure.

### Candidate Observable Events

- Device availability
- Interface state changes
- WAN link state changes
- Routing adjacency changes
- Route availability changes
- Configuration-related events where observable
- Device-generated warnings and errors

### Desired Attributes

Where technically available:

- Timestamp
- Device identity
- Device/site
- Interface
- Event type
- Event severity
- Event description
- Previous/current state

### Research Relevance

This telemetry supports observation of infrastructure behavior such as
the WAN and routing events previously investigated during RC-001.

---

## 4. Network Communication Telemetry

### Purpose

Provide visibility into communication patterns between systems and
network segments.

### Candidate Observable Attributes

Where technically available:

- Timestamp
- Source address
- Destination address
- Source port
- Destination port
- Transport protocol
- Source network or VLAN
- Destination network or VLAN
- Session or flow duration
- Packet count
- Byte count
- Connection state

### Research Relevance

Communication telemetry may allow RC-002 to characterize normal traffic
patterns and compare them with controlled abnormal activity.

The project shall not assume that every attribute is available until
technology evaluation is completed.

---

## 5. Security-Control Telemetry

### Purpose

Observe events generated by security mechanisms already protecting the
enterprise environment.

### Candidate Observable Events

- ACL permit activity
- ACL deny activity
- Management-access attempts
- Successful administrative access
- Failed administrative access
- Policy-related events where technically available

### Desired Attributes

- Timestamp
- Source
- Destination
- Relevant protocol or service
- Permit/deny result
- Security control or device producing the event

### Research Relevance

This category allows RC-002 to examine whether security controls produce
sufficient telemetry to explain observed access behavior.

---

## 6. Host and Service Telemetry

### Purpose

Provide selected visibility into designated enterprise hosts and
infrastructure services where supported by the experimental environment.

### Candidate Sources

- Operating-system events
- Authentication events
- DNS activity
- Web-service activity
- Infrastructure-service events
- Application/service availability events

### Desired Attributes

Where technically available:

- Timestamp
- Host identity
- Service identity
- Event type
- Event outcome
- Source address
- User/account context
- Relevant event description

### Research Relevance

Host and service telemetry can provide additional context that may not be
visible from network infrastructure telemetry alone.

---

## 7. Experimental-Context Telemetry

### Purpose

Preserve information required to associate collected telemetry with
controlled experiments.

### Required Context

Each experiment should record:

- Experiment identifier
- Test scenario
- Start time
- End time
- Source system
- Target system where applicable
- Expected observable behavior
- Actual observable behavior
- Relevant evidence location

### Research Relevance

Experimental context prevents analysts from relying solely on memory when
interpreting collected events and supports repeatability.

---

## 8. Telemetry Lifecycle

The conceptual RC-002 telemetry lifecycle is:

**SOURCE → COLLECT → TRANSPORT → CENTRALIZE → STORE → SEARCH → ANALYZE → EVIDENCE**

### Source

The system or device producing observable information.

### Collect

The mechanism used to obtain telemetry.

### Transport

The method by which telemetry reaches the centralized environment.

### Centralize

Aggregation of telemetry from distributed sources.

### Store

Retention of collected information for analysis.

### Search

Retrieval or filtering of relevant telemetry.

### Analyze

Comparison and interpretation of observed behavior.

### Evidence

Preservation of information supporting experimental findings.

---

## 9. Minimum Telemetry Context

Where technically supported, collected telemetry should preserve enough
context to answer:

1. **When** did the event occur?
2. **Where** did it originate?
3. **What** occurred?
4. **Which systems** were involved?
5. **What was the observed outcome?**

Not every telemetry source will necessarily provide all five elements.

Any missing context that affects experimental interpretation shall be
documented as a limitation.

---

## 10. Telemetry Priority Levels

### Priority 1 — Required

Telemetry necessary to answer the primary research question.

Initial Priority 1 categories include:

- Network infrastructure events
- Selected communication activity
- Selected security-control events
- Reliable timestamps
- Source identification

### Priority 2 — Desired

Telemetry that improves analytical context but may not be essential for
minimum experimental validation.

Examples may include:

- Host authentication events
- Service-specific logs
- Detailed traffic-volume statistics
- Additional metadata

### Priority 3 — Future Research

Capabilities that may support later Project Aegis stages but are not
required for RC-002.

Examples include:

- Automated threat classification
- Machine-learning anomaly scoring
- Automated incident response
- Adaptive defensive controls

---

## 11. Relationship to Project Aegis

RC-002 establishes the observational foundation required by subsequent
Project Aegis stages.

BUILD → HARDEN → **OBSERVE** → DETECT → INVESTIGATE → RESPOND → ADAPT

RC-002 focuses on making behavior measurable and visible.

The existence of telemetry shall not, by itself, be interpreted as
successful threat detection.
